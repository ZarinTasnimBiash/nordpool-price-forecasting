The task

At around 11:00 on day D — before the Nord Pool day-ahead auction closes at 12:00 — forecast the 24 hourly prices for delivery day D+1 in bidding area SE3.

Every feature must be knowable before that cutoff. That constraint drives the whole design, and it is enforced by an automated audit that refuses to build the training table if any feature reaches past it. All four Swedish bidding areas (SE1–SE4) are collected so neighbouring-area prices can be used as predictors.

"Available at the cutoff" is not the same as "about the past." A weather forecast for tomorrow, published before 11:00, genuinely existed at 11:00 — so using it is legitimate. Only tomorrow's actual observations are unavailable. Getting that distinction right turned out to be the single largest improvement in the project.

The third lane is the distinction that took two attempts to get right. Treating both the forecast and the observation as leakage — the original design — threw away the project's largest signal.

How the pipeline is built

The command line and the scheduler call the same collection functions, so manual backfills and automatic daily runs cannot diverge. Every arrow is re-runnable: writes replace a partition rather than appending, so any day can be rebuilt safely.

An honest gap: Dagster schedules two of the four sources — Nord Pool prices at 13:30 and SMHI weather at 00:30. The historical price source and the forecast archive are driven by the CLI only, because both are backfills rather than daily feeds.

Stage 5 results

Three baselines, none of them strawmen. The one that counts is "tomorrow at 18:00 will cost whatever today at 18:00 cost" — it needs no data pipeline at all, and the lag-24 autocorrelation is 0.677. Any model that does not clear it comfortably has not earned its existence.

Why walk-forward, and not a single holdout

The single split used in stage 4 turned out not to be representative: its test window had nearly double the training median price and almost no negative hours. That is a change of regime, not a sampling wobble, so one score says as much about the window as about the model.

The justification is in the benchmark's own numbers: the same naive rule scored anywhere from 14.0 to 35.8 depending on which single month was chosen. One split could have proved almost anything. Hyperparameters were chosen on the orange folds and frozen before the green ones were touched.

The noise rule, instead of a success threshold

A fixed target was considered and rejected as circular — any threshold would have been set just under what had already been achieved. Instead: keep a change only when its improvement survives a block bootstrap over whole days. Whole days, never individual hours, because neighbouring hours correlate about 0.95; resampling hours independently would pretend there is far more independent evidence than there is and would rubber-stamp everything.

The control that reframed the stage

"Gradient boosting beats the naive baseline by 25.6%" is ambiguous as it stands. It could be the algorithm — or it could be the feature engineering, which any model would have benefited from. Nothing in the stage separated the two, so ridge regression was run on the identical 70 features, tuned with the same discipline on the same five tuning folds.

Measured · changed how the stage should be reported

Of the 6.72 EUR/MWh the model gains over the naive baseline, 6.61 is available to a linear model on the same features. Gradient boosting is worth +0.11, 95% CI [−0.72, +0.93] — not distinguishable from noise.

Almost all the value in this project came from the feature engineering and the leakage discipline of stage 4 — above all the archived weather forecasts — and almost none from the learning algorithm. That is the opposite of where effort usually goes, which is exactly why it was worth measuring rather than assuming.

Boosting still ships, on a different argument. Look at the spread rather than the centre: ridge swings from 14.4 to 24.2 across folds where boosting holds 16.5 to 22.2, and ridge's bad days are worse (p90 day 34.42 against 31.59). Ridge owns both the best single fold and the worst. Boosting is not more accurate — it is more consistent across regimes and better when things go wrong, which for a number someone bids against is the property worth having. Keeping it on a stability argument is defensible; keeping it on an accuracy argument would not have been.

Two things gradient boosting handled for free had to be done explicitly for ridge, both fitted inside the pipeline so they only ever see the training fold: median imputation (ten weather columns have real gaps up to 13.1%; trees learn a direction to send a missing value, ridge cannot accept one at all) and standardisation (features run from prices in the hundreds to sine encodings in [−1, 1], and ridge penalises each coefficient equally). Chosen alpha 1000, with the grid deliberately extended past it on both sides — a best value sitting at the edge of its grid is a statement about the grid, not the model.

Prediction intervals

A point forecast whose typical miss is a third of the price level invites false confidence. The standard was fixed before anything ran, so it could not be renegotiated afterwards: an interval that claims 80% and delivers 55% is worse than no interval at all.

IntervalStatedActualBelowAboveWidthVerdict
quantile, MAE early stopping80%57.9%13.7%28.5%39.5unusable
quantile, pinball early stopping80%70.3%13.2%16.5%51.7overconfident

Failure 1 · a real bug, now fixed

Early stopping graded every model with MAE, regardless of the loss being fitted. MAE is minimised by the median, so judging a 90th-percentile model by MAE stops it exactly where it is least like a 90th-percentile model. Every quantile model stopped at the wrong number of trees. The fix scores the validation slice with pinball loss at the model's own quantile.

The clue was the shape of the failure: twice as many outcomes fell above the interval as below, which says the ceiling specifically was too low rather than the range being uniformly narrow. The bug was invisible — nothing crashed, the point forecast was unaffected, and the intervals looked like plausible intervals. It was caught only because coverage was measured against a number fixed in advance.

Failure 2 · not a bug at all

Quantile regression is overconfident by construction. Its quantiles are fitted on training rows, so they describe how wrong the model was on data it had already seen, which is always less wrong than it will be tomorrow.

Conformal calibration corrects it by measurement rather than trust: hold back the last 15% of the training period in time order, measure how far outside the interval the truth actually fell on those unseen rows, and pad by exactly that much. The padding is signed, so an interval that was already too wide would shrink. It was positive on all ten folds (+1.41 to +7.48) — the raw quantiles were too narrow in every single month. The calibration slice is deliberately the most recent stretch, because this project has already been bitten once by a regime change.

Three caveats that travel with the 80.4%

  • The interval is wide — 66.4 EUR/MWh against a test-period mean price near 59. That is the measurement, not a flaw in the method: day-ahead prices genuinely are that uncertain 13–36 hours out, and the earlier narrower intervals were narrow by being wrong. It does limit how much a bidding decision can lean on them.
  • It is still asymmetric — 5.5% below, 14.1% above. The padding is symmetric, so it overcorrects the floor and undercorrects the ceiling. Prices are right-skewed (SE3 reaches €707 against a median near 36). A separate pad per side is the obvious next step and is not done.
  • It costs the point forecast — holding 15% back for calibration moves the median model from MAE 19.56 to 20.40. The plain model and the interval wrapper ship separately; the point forecast must not be read off the interval's midpoint.

How the model actually decides

Everything above says the model works. This traces how, through one real hour, using the real fitted model — every number below was read out of the trained object, not invented for the explanation.

The hour being predicted

Thursday 15 January 2026, 18:00. Evening peak, midwinter — the hardest and most valuable kind of hour. It falls in a reporting fold, so the model had never seen it.

What it was worth

Actual price 104.42 EUR/MWh, against 15,357 training rows and 70 features describing that hour.

Step 0 · one guess for every hour

Before a single tree exists, the model predicts the same number for everything: the average price across its training rows.

starting guess = mean of 15,357 training prices = 38.81
actual 104.42 → this guess is wrong by 65.61

Every tree that follows exists only to shrink that 65.61. Gradient boosting never predicts a price directly — it predicts corrections to the guess so far.

Step 1 · the first tree asks three questions

A tree is a chain of yes/no questions ending in a number. This is the actual path the first tree took for this hour — the real feature names, the real thresholds it chose, and the real values this hour carried:

The tree asksThis hourAnswerGoes
spot_price_se3_lag_24h ≤ 57.67?108.20noright — into the expensive branch
spot_price_se4_lag_24h ≤ 140.69?170.61noright — the southern zone was expensive too
wind_speed_se4_fc2 ≤ 16.10?20.50noright — and it will be windy in the south
leaf reached — the tree's contribution+2.00

Read that as one sentence: "yesterday was expensive here, yesterday was very expensive in the south, and tomorrow will be windy in the south." Note the third question — it is a forecast, legitimately available at the 11:00 cutoff. The tree is using tomorrow's weather because tomorrow's weather was already knowable.

A single leaf is not interpretable on its own. High wind normally pushes prices down, yet this leaf adds. It is a relative adjustment applied inside an already-expensive branch, not a statement that wind raises prices.

Step 2 · why only +2.00?

Left to itself the tree wanted to add about +40. It was allowed +2.00, because every tree's answer is multiplied by the learning rate before being added:

38.81 + (0.05 × 40.06) = 38.81 + 2.00 = 40.81

This deliberate timidity is the central trick. One tree that leaps the whole distance would carry all of its own mistakes with it. Two hundred trees each nudging 5% of the way let later trees correct earlier ones, so errors average out instead of compounding.

Step 3 · every later tree is trained on what is left over

Tree 2 does not see the price 104.42. It sees the residual — what tree 1 failed to explain — and tries to predict that. Tree 3 sees what trees 1 and 2 together still miss.

On this particular hour, the naive baseline beat the model.

The model said 114.22 against an actual 104.42 — a miss of 9.80. "Yesterday at 18:00" said 108.20, a miss of 3.78. That is not a flaw in the example, it is the point of showing a real one. The model wins on average — 19.56 against 26.28 across 7,008 hours, and on 10 of 10 folds. It does not win every hour, and an explanation that only showed hours where it did would be selling something.

Step 5 · when to stop — overfitting made visible

More trees always fit the training data better. That is exactly the danger: past a point the model stops learning how electricity prices behave and starts memorising the particular hours it was shown. Both curves below come from the same fold — one measures error on data the model trained on, the other on 2,303 hours it was not allowed to see.

After roughly 150 trees the honest curve is flat. The next 450 trees improve performance on unseen data by 0.17 EUR/MWh while training error drops by a third — that difference is memorisation, and it buys nothing.

Early stopping automates the judgement: grow trees in batches of 25, check the held-out slice after each batch, stop once four batches in a row fail to improve it. The detail that matters most — the held-out slice is the last stretch of the training period in time order, never a random sample. Neighbouring hours are about 95% alike, so a random slice would put 14:00 in training and 15:00 in validation, and the model would be graded on an answer it had effectively already been given.

Learning rate — how big a step each tree takes

0.05 here. Lower is more cautious and needs more trees; higher gets there faster and overshoots. It trades against tree count almost exactly: 0.03 stopped at 225 trees, 0.15 at 50.

Number of trees — how many corrections in total

Not chosen by hand. Early stopping picks it per fold by watching held-out error, so a fold with more history can grow a larger model without anyone deciding that in advance.

Overfitting — memorising instead of learning

Visible as the widening gap above: training error 6.61 against 20.27 on unseen data. The training number is not a performance figure — it measures how much was memorised.

Early stopping — knowing when to quit

scikit-learn's built-in version picks its validation slice at random, which is both non-reproducible and wrong for a time series, so it is reimplemented here chronologically.

Stage 6 — what the validation found

Stage 5 asked is the model good? and answered yes, on average. Stage 6 asks where it is bad, whether it is bad for reasons that make physical sense, and whether every feature earns its place. Measured on the same ten reporting folds — 7,007 hours. Three earlier conclusions did not survive.

The model shrinks — and that one fact explains three separate symptoms

Mean signed error by true price band, EUR/MWh. The model over-predicts cheap hours and under-predicts expensive ones — regression to the mean. The aggregate figure of −4.50 is the weighted average of two opposite biases, so "the model runs low" is only true above about €50.

That single mechanism accounts for three things previously treated as separate problems:

  • Why it adds nothing on spikes. On the 58 hours above €200 it under-predicts by 98 on average — saying about 154 when the truth is 252. It is not failing to model spikes, it is actively shrinking them.
  • Why it adds nothing on negative hours. The same effect at the other end: +8.18 against a true mean of −1.53.
  • Why the interval misses high more than low. The centre of the interval is pulled down on exactly the expensive hours where the outcome is most likely to be extreme.

An explanation I had published, now refuted.

Earlier versions of this page and of docs/05_modeling.md argued that the bias and the interval asymmetry might both come from trees being unable to predict above their training maximum. Measured: 0 of 7,007 test hours had a true price above their fold's training maximum. The mechanism cannot apply and the claim has been removed. The regime-shift explanation is also weak — correlation between a month's price shift and its bias is −0.327, with stark counter-examples.

spot_price_se3_lag_24h alone scores 5.712 — one feature is worth more than every weather column combined. Worth knowing before proposing more data sources.

The stage 3 wind finding does not transfer.

Exploration reported that northern wind predicts SE3's price better than local wind (−0.260 against −0.239). In the fitted model the opposite holds: wind_speed_se3_fc2 scores 1.552 against wind_speed_se1_fc2 0.331. The explanation is that these are different variables — on the forecast columns the model actually uses, the two zones are tied (−0.297 against −0.296). The stage 3 ranking was measured on contemporaneous observed wind and does not carry over.

A second thing falls out: the observed 24-hour means correlate only −0.088 to −0.118 with tomorrow's price. Averaging over 24 hours and shifting to a cutoff destroys about two-thirds of the association — a better explanation of why observed weather looked worthless in stage 4 than the "redundant with price lags" story told at the time.

Reversal · the decision to keep them is vindicated

The 24 observed-weather columns now earn their place: +0.826, 95% CI [+0.289, +1.329]. Stage 4 measured +0.07 with an interval spanning zero and the decision recorded was explicitly "keep them, re-test once the model is stronger". The re-test says keep them for real.

A methodological note worth carrying: permutation rates that whole family at only 0.464, but removing it costs 0.826. Both are correct measurements of different things — permutation shuffles one column at a time, so four correlated temperature columns each look useless because the other three still carry the signal. Single-column importance systematically understates correlated groups; group decisions need group ablations.

A change deliberately not made

The ten rolling-price features have negative permutation importance, and dropping them improves the reporting folds by +0.406, CI [+0.093, +0.708] — apparently a free improvement. It was not adopted, for two reasons.

  • That measurement was made on the reporting folds, which exist so that no modelling decision is made using them. "Keep" costs nothing; "change" would mean the holdout had influenced the model.
  • Decisively, the tuning folds disagree in sign: dropping them there is worth −0.113, CI [−0.337, +0.103], not distinguishable from noise. A change that helps in one period and hurts in another has not been shown to be an improvement — it has been shown to be unstable.

Findings worth knowing

Everything below was discovered by testing against live systems, or by checking whether a result was plausible — not assumed from documentation. Each one changed the design. None of them crashed anything.

The largest single improvement · reversed an earlier decision

Weather forecasts are worth 3.9 EUR/MWh; observed weather is worth nothing. The original design excluded all "tomorrow weather" as leakage. That was too broad — a forecast published before the cutoff genuinely existed at the cutoff. Measured on 4,344 held-out hours: observed weather adds +0.07 with an interval spanning zero, while forecasts for the delivery hour add +3.89. Observed weather is redundant because yesterday's weather is already in yesterday's prices; tomorrow's forecast is not.

The control · changed how the result should be reported

Ridge regression on the same 70 features scores 19.67 against boosting's 19.56 — a difference of +0.11 with a confidence interval spanning zero. The 25.6% improvement belongs to the feature engineering, not to the choice of algorithm. Boosting ships on a stability argument (fold spread 1.92 against 3.13), not an accuracy one.

Data availability · changed the source list

The public Nord Pool API only serves a rolling ~62-day window. Anything older returns 401, so it could never supply training history. elprisetjustnu.se now provides three years, with Nord Pool retained for live daily collection. The two agree exactly across 19,200 overlapping hours — mean and max difference 0.0000 EUR/MWh — which is what licenses trusting the historical source. The window genuinely rolls: the Dagster partition count has already fallen from 65 to 56.

Leakage · caught by an automated audit

Two bugs that would have inflated results silently, both on the 25-hour daylight-saving day. A fixed 24-hour price lag cannot escape a 25-hour delivery day — for the last hour it lands on the first hour of the same day, a price from the same unpublished auction. And "one day earlier" computed as 24 elapsed hours drifted the 11:00 cutoff to 12:00, handing the model an extra hour it would not have had. Three target hours are dropped; the cutoff arithmetic now runs on the calendar rather than the clock. Both have regression tests.

Wrong criterion · broke the prediction intervals

Early stopping graded quantile models with MAE. MAE is minimised by the median, so a 90th-percentile model was stopped exactly where it was least like a 90th-percentile model. The 80% intervals covered 57.9%. Fixed by scoring with pinball loss at the model's own quantile, then calibrated conformally to 80.4%. Nothing errored at any point; only a coverage check fixed in advance caught it.

Reproducibility · invalidated a conclusion

An early version of the weather experiment could not be reproduced, and the conclusion drawn from it was wrong. Repeat runs of identical code disagreed by ~0.3 EUR/MWh — the same size as the effects being measured. Two causes: scikit-learn enables early stopping above 10,000 rows using a random validation split (also wrong for a time series), and DuckDB's parallel avg() is not bitwise reproducible — its floating-point summation order varies between runs, shifting gradient-boosting bin edges and changing tree splits. Fixed with threads=1. The full pipeline now reproduces every number bit for bit across runs.

Silent failures · why every result now carries an interval

Three separate bugs produced no error at all: a timezone dropped during a lookup matched 0 of 1,083 rows and filled every weather column with nulls; a configured Nord Pool endpoint returned 404 because its path had been guessed rather than observed; and fetching only SMHI's quality-checked archive left a silent 3.5-month hole at the recent end. All three were caught by asking "is this result plausible?" rather than by anything crashing. Model comparisons are now reported with bootstrap confidence intervals so a difference is only claimed when it exceeds the noise.

Simplified or left out

  • Kubernetes deployment — runs under dagster dev locally. Deployment is not the learning goal.
  • Sensors — the reference platform triggers downstream work when upstream data lands; here the feature build is run explicitly.
  • TimescaleDB operational writes and bidding flows — require real trading infrastructure.
  • Partial orchestration — Dagster schedules Nord Pool and SMHI. The historical price source and the forecast archive are CLI-only, since both are backfills rather than daily feeds.
  • No schema class for the feature table — a deliberate exception, because its columns churn through modelling. The guarantees that matter (unique keys, no grid gaps, no all-null block, no leakage) are asserted in code and covered by tests instead.
  • ENTSO-E load, generation and reservoir data — free with a token, and the most obvious remaining gap. There is currently no demand-side signal at all.

Questions for review

Decisions that belong to the supervisor rather than to the code.

1. Is the substitute price source acceptable?

Three years of history comes from elprisetjustnu.se, a free public service republishing Nord Pool prices, because the public API only covers ~62 days. It has been cross-checked and agrees exactly — but if there is a preference for ENTSO-E or the partner API, that is better changed now.

2. Is the public forecast archive an acceptable stand-in?

Forecast data has been brought in from Open-Meteo's previous-runs archive, and it is worth 3.9 EUR/MWh — the single largest improvement in the project. The remaining question is whether a public community archive with no SLA is acceptable, or whether the in-house MET pipeline should be the source. Note the cost: coverage starts 2024-04, which shortened training history by five months.

3. Should ENTSO-E load and generation data be added?

It is free with a token and is the most obvious gap in the feature set — there is currently no demand-side signal at all. Against that, it means new ingestion work after the modelling stage is already complete.

4. Is a 66 EUR/MWh-wide interval useful for a bidding decision?

It is honestly calibrated at 80.4%, but it is about as wide as the price level itself. Narrowing it means a better model, not a different interval method — the width is the uncertainty, measured.

5. Is SE3 alone the right target?

Currently forecasting SE3 only, using the other zones as predictors. Extending to all four is feasible but widens the scope.

6. Is 25.6% over a naive baseline good enough to stop tuning the point forecast?

No threshold was set, deliberately — a fixed target was rejected as circular. The noise rule says to stop when changes stop being distinguishable from noise, and the ridge control suggests the remaining gains are in features and data, not in the algorithm.

7. Given that the model shrinks, is it fit for the intended purpose?

Stage 6 showed it is reliable in the ordinary middle of the price distribution and adds nothing at either extreme — on spike hours above €200 and on negative hours it matches "yesterday's price" and no better. If the bidding process cares mainly about extreme hours, that is a design problem rather than a tuning problem, and worth knowing now.
